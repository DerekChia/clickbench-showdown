# Design Review: dashboard/index.html

**Review ID:** dashboard_index_20260726_083624
**Reviewed:** 2026-07-26 08:36
**Target:** `dashboard/index.html`
**Focus:** visual design, usability
**Platform:** desktop only

## Summary

A single-file vanilla-JS dashboard with a coherent dark palette, a disciplined
token set, and a sensible three-font role split (serif for figures, mono for
data, sans for chrome). The visual language is consistent and the data density
is appropriate for a benchmark tool.

The problems are concentrated in two places: the interface is effectively
unusable without a mouse, and the secondary text colour — which carries most of
the labelling in the UI — fails WCAG AA against two of the three surfaces it
sits on. One CSS custom property is referenced but never defined.

## Critical Issues

### Issue 1: The dashboard cannot be operated from the keyboard

**Severity:** Critical
**Location:** `dashboard/index.html:85-96` (buttons), `:995` (row wiring)
**Category:** Usability

**Problem:**
Two compounding gaps.

1. `button` has no `:focus` or `:focus-visible` rule anywhere in the
   stylesheet. The only focus style in the file is on the two `<select>`
   elements (`:110`), and it *removes* the native outline in favour of a 1px
   border-colour change.
2. Query rows are made interactive with an `onclick` attribute alone:
   `tr.setAttribute('onclick', 'toggleRow(' + i + ')')`. There is no
   `tabindex`, no `role`, no `keydown` handler and no `aria-expanded`.

**Impact:**
A keyboard user tabbing through the header sees no indication of where focus
is, across all seven buttons. And the expandable rows — which hold the SQL, the
`docker exec` one-liners and the per-query charts, i.e. most of the analytical
value of the page — cannot be opened at all. Screen-reader users get no signal
that the rows are interactive or that they expand.

**Recommendation:**
Restore a visible focus ring globally, and promote the rows to real controls.

**Code Example:**

```css
/* Before: no button focus style at all; selects strip the outline */
.db-select:focus, .files-select:focus { outline: none; border-color: var(--color-a); }

/* After: keep the custom border treatment, but never remove the ring */
:where(button, select, [role="button"]):focus-visible {
  outline: 2px solid var(--color-a);
  outline-offset: 2px;
}
.db-select:focus, .files-select:focus { border-color: var(--color-a); }
```

```js
// Before
tr.setAttribute('onclick', `toggleRow(${i})`);

// After
tr.tabIndex = 0;
tr.setAttribute('role', 'button');
tr.setAttribute('aria-expanded', 'false');
tr.setAttribute('aria-controls', `expand-${i}`);
tr.addEventListener('click', () => toggleRow(i));
tr.addEventListener('keydown', e => {
  if (e.key === 'Enter' || e.key === ' ') { e.preventDefault(); toggleRow(i); }
});
// and in toggleRow(): tr.setAttribute('aria-expanded', String(expandedRows.has(i)))
```

## Major Issues

### Issue 2: `var(--fg)` is referenced but never defined

**Severity:** Major
**Location:** `dashboard/index.html:205`, `:459`
**Category:** Visual

**Problem:**
`.db-chip .db-name { color: var(--fg); }` and
`.btn-copy:hover { ... color: var(--fg); }` both reference `--fg`. The token
set at `:root` defines `--txt`, not `--fg`. With no fallback, both declarations
are invalid at computed-value time and the property inherits instead.

**Impact:**
Database names in the status chips render in the inherited body colour rather
than the intended emphasis colour, so the `font-weight: 600` is doing the
distinguishing work alone. The copy button's hover state changes background but
not text colour, making the hover feel half-applied. It is silent — nothing
errors — which is why it has survived.

**Recommendation:**
Use the token that exists. If a distinct `--fg` is wanted, define it.

```css
/* Before */
.db-chip .db-name { color: var(--fg); font-weight: 600; }
.btn-copy:hover   { background: #2a3f55; color: var(--fg); }

/* After */
.db-chip .db-name { color: var(--txt); font-weight: 600; }
.btn-copy:hover   { background: #2a3f55; color: var(--txt); }
```

### Issue 3: Secondary text fails WCAG AA on cards and panels

**Severity:** Major
**Location:** `dashboard/index.html:22` (`--mu`), used at `:206`, `:222`, `:236`, `:303`, `:352`, `:499`
**Category:** Visual

**Problem:**
`--mu: #6A8BA8` is the colour for nearly all secondary text. Measured against
the three surfaces it is used on:

| Foreground | Background | Ratio | AA (4.5:1) |
|---|---|---|---|
| `--mu` | `--bg` `#111B26` | 4.86:1 | pass |
| `--mu` | `--panel` `#18242F` | **4.41:1** | **fail** |
| `--mu` | `--card` `#1E2E3D` | **3.88:1** | **fail** |

The failing surfaces carry the summary-card labels and sub-labels, the table
column headers, the run counts, the chip row counts and the expand-panel
headings — at `.68rem`–`.72rem`, which is 9.5–10px at this root size.

**Impact:**
This is small text at low contrast, and it is what labels every number on the
page. It is the difference between "p50" being readable at a glance and being
guessed from position.

**Recommendation:**
Lighten `--mu` until it clears 4.5:1 on the lightest surface it is used on
(`--card`). `#7FA3C0` measures 5.35:1 on `--card` and 6.7:1 on `--bg`, keeping
the same hue family. Alternatively introduce `--mu-on-card` for the two
offending surfaces.

### Issue 4: The `docker exec` label is at 2.58:1

**Severity:** Major
**Location:** `dashboard/index.html:474-483`
**Category:** Visual

**Problem:**
`.exec-cmd-label` sets `color: var(--mu)` *and* `opacity: .6`, over the
`#0D1B26` expand-panel background. The composite is 2.58:1 — below AA for
normal text (4.5:1) and below even the large-text threshold (3:1), at
`.6rem` (8.4px).

**Impact:**
The "Run on host" label that explains what the command block underneath is for
is the least readable text on the page, and it is the one piece of instructional
copy in the expanded view.

**Recommendation:**
Drop the opacity; the colour is already the muted token.

```css
/* Before */
.exec-cmd-label { font-size: .6rem; color: var(--mu); opacity: .6; ... }

/* After */
.exec-cmd-label { font-size: .68rem; color: var(--mu); ... }
```

### Issue 5: Root font size is pinned to 14px

**Severity:** Major
**Location:** `dashboard/index.html:29`
**Category:** Visual / Usability

**Problem:**
`html { font-size: 14px; }` overrides the browser's root size. Every other size
in the sheet is expressed in `rem`, so the whole scale is anchored to that
value — and the smallest steps land at `.6rem` = 8.4px and `.68rem` = 9.5px.

**Impact:**
A user who has raised their default browser font size for readability gets no
benefit here; the page ignores the preference entirely. Page zoom still works,
but zoom scales layout too, which on a dense 16-column table means horizontal
scrolling rather than larger text.

**Recommendation:**
Set the root in relative units so preference is respected while keeping the
current visual size as the default: `html { font-size: 87.5%; }` (= 14px at a
default 16px root). Then raise the floor of the scale — nothing below `.7rem`.

### Issue 6: All error feedback goes through blocking `alert()`

**Severity:** Major
**Location:** `dashboard/index.html:900`, `:910`, `:923`, `:1542`
**Category:** Usability

**Problem:**
Four distinct failure paths — duplicate database selection, a backend-rejected
selection, an unreachable backend, and a refused benchmark start — all surface
as `alert()`. Meanwhile the page already has a non-blocking inline convention:
`#reload-msg` with `.ok` / `.err` modifiers (`:141-147`), and the loader banner.

**Impact:**
A modal halts the 1s polling loop's visible updates behind an OS dialog, has to
be dismissed before anything else can be read, and discards the message the
moment it closes — so a user cannot compare the error against the state that
produced it. It is also inconsistent with how the same page reports loader
outcomes.

**Recommendation:**
Route these through the existing inline mechanism, e.g. reuse `#reload-msg` or
the loader banner with `role="status"` so assistive tech announces it:

```js
// Before
alert('Please select two different databases.');

// After
showMessage('Please select two different databases.', 'err');
```

### Issue 8: `#loader-banner.ready` is dead CSS

**Severity:** Minor
**Location:** `dashboard/index.html:180`
**Category:** Code / Visual

`#loader-banner.ready { border-left-color: var(--green); display: none; }`

### Issue 9: Status glyphs carry no text alternative

**Severity:** Minor
**Location:** `dashboard/index.html:965-973` (`statusIcon`), `:999`, `:1006`
**Category:** Usability

Per-query status is rendered as a bare glyph — `·`, `✓`, `●`, `✕`, `!`. Good
practice that it is *not* colour-alone, but `✕` and `!` announce as punctuation
or get skipped entirely by a screen reader. Give the cell an `aria-label`
("timeout", "error", "ok") or a visually-hidden span.

### Issue 11: Header packs twelve controls into one undifferentiated row

**Severity:** Minor
**Location:** `dashboard/index.html:535-564`
**Category:** Visual / Usability

The header right side holds a status dot, run label, active-DB badge, two
selects, Apply, a file-count select, Load Data, a message span, Start, Stop and
Export CSV — separated by three ad-hoc `<div style="width:1px;height:20px">`

give the file-count select a visible label, e.g. "Load ⌄ files".

## Suggestions

### Suggestion 1: Explain why Start is disabled

**Location:** `dashboard/index.html:1362`
**Category:** Usability

`$('btn-start').disabled = d.running || !rowsMatch;` — a user looking at a
greyed-out Start with a green "Ready" banner has no way to tell that the row
counts differ. The banner does say so when both counts are non-zero, but the
button itself carries no explanation. Set a `title` on the disabled button
mirroring the reason ("Row counts differ by more than 1%", "Benchmark already
running").

---

### Suggestion 2: Make the summary grid tolerant of long names

**Location:** `dashboard/index.html:210-215`
**Category:** Visual

`grid-template-columns: repeat(5, 1fr)` at a 1400px max width gives each card
~265px. The labels are database-name-driven ("TimescaleDB Total Runs",
"PostgreSQL Timeouts"), so the longest pairs wrap to two lines while others stay
on one, leaving the value baselines misaligned across the row.
`repeat(auto-fit, minmax(220px, 1fr))` plus a fixed `min-height` on `.label`
keeps the baselines aligned regardless of name length.

## Positive Observations

- **Token discipline.** Colours, fonts and radii come from `:root` custom
  properties rather than literals, and the per-database accent colours are
  driven through `--color-a` / `--color-b` at runtime, so the whole UI
  recolours from one place when the selection changes.
- **Status is not colour-alone.** `statusIcon` pairs every state with a distinct
  glyph as well as a colour class — the single most commonly missed
  accessibility requirement in dashboards, handled correctly here.
- **Timing colours are high-contrast.** The semantic timing palette measures
  5.71:1 (red) to 10.32:1 (yellow) against the panel — comfortably AA, which is
  exactly right for the numbers that carry the meaning.
- **Real loading and empty states.** A spinner plus a specific message, and
  buttons that reflect readiness, rather than a blank page while data loads.
- **Typographic roles are consistent.** Serif for headline figures, mono for all
  data and identifiers, sans for chrome — applied without exception throughout.
- **SQL is escaped before injection.** `escHtml` is applied to query text and
  generated shell commands before they reach `innerHTML`.
